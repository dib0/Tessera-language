# Tessera language repository

Tessera is a programming language for LLMs, not humans: decisions about syntax and the library are made by measurement (`harness/`), not by taste. This repository holds the specification, the compilers, the runtime, the standard modules and the examples.

To write Tessera code (examples, `std/`, `stage1/`, tests), use the `tessera` skill in `skills/tessera/`, or read `harness/reference/tessera.md` first. This file covers working on the language itself.

## Layout

- `language-design.md`: the authoritative specification (draft number at the top). When compiler and spec disagree, the spec wins, unless the spec is changed by an explicit decision. Section 3 lists the changes per draft; section 19 holds open questions and findings.
- `compiler/`: stage 0, in Rust, zero dependencies. **Frozen** at draft 0.3 plus `process` and `file_exists`. It stays as the independent reference for the parity tests; do not add features to it.
- `stage1/`: the compiler in Tessera (entry `stage1/main.tes`; modules `source`, `lexer`, `ast`, `parser`, `checker`, `codegen`). All new language features go here.
- `bootstrap/tessera1.rs`: the seed, the Rust that stage 1 generates for itself. Generated; never edit by hand (see `bootstrap/README.md`).
- `runtime/`: Rust runtime embedded in generated programs. `core.rs` is shared with stage 0 (keep its signatures); `extra.rs`, `web.rs`, `ui.rs` (X11), `win32.rs` (the Windows window), `audio.rs` and `winmm.rs` (the Windows sound card) are stage 1 only. `adapter.rs`, `win32.rs` and `winmm.rs` are the only files allowed to contain `unsafe`: they are the operating system's C interfaces and nothing else belongs there.
- `std/`: standard modules written in Tessera, embedded into the compiler.
- `stage1/runtime_text.tes`: generated by `tools/embed_runtime.tes` from `runtime/` and `std/`. Never edit; run `./build.sh`.
- `hosts/`: nginx, Apache and IIS modules that load `--library` builds.
- `harness/`: model-based measurement (see `harness/README.md`). `harness/reference/tessera.md` is the reference the model gets.
- `skills/tessera/`: the Claude Code skill; `reference.md` and `language-design.md` in it are symlinks.
- `examples/tesseradoom/`: DOOM-style engine as a proof point; decisions in `docs/doom-decisions.md`. WAD files are never committed.
- `docs/status.md`: test and roadmap status per draft. `application-roadmap.md`: gaps for real applications.

## Build and test

The Rust toolchain may not be on `PATH` in a non-login shell: `export PATH=$HOME/.cargo/bin:$PATH`.

On Windows everything below runs in Git Bash; `build.sh` adds the `.exe` extension itself. Two features need a program that is not part of Windows: `db` needs `sqlite3` on `PATH` (`winget install SQLite.SQLite`), and `python3` for the Tesseradoom checks is usually the Microsoft Store placeholder, so those checks fall back to `python` and skip themselves when neither is a real Python 3.

Two Git Bash traps when a *native* program is involved. It does not understand a path such as `/tmp/x` that `mktemp -d` gives (use `cygpath -m`), and it rewrites an argument that looks like one before the program sees it, so `app request GET /fail` arrives as `GET C:/Program Files/Git/fail`; `export MSYS_NO_PATHCONV=1 MSYS2_ARG_CONV_EXCL='*'` turns that off. `examples/tesseradoom/checks/run_checks.sh` and `runtime/tests/run_web_tests.sh` do both already.

```sh
./build.sh                               # stage 0, runtime embedding, seed -> bootstrap -> bin/tessera1, fixpoint check, tools/xsend
cd compiler && cargo test --release      # the whole suite, stage 0 and stage 1 (a few minutes)
cargo test --release --test stage1 <name>  # a single stage 1 test function
bin/tessera1 test tests/std/math_test.tes  # one std module test
bin/tessera1 format --check examples std stage1 tools
```

Run `./build.sh` before the test suite after any change to `stage1/`, `runtime/` or `std/`; the suite uses `bin/tessera1` and checks that `stage1/runtime_text.tes` is up to date.

Test locations (the expected error or runtime code is the start of the file name, e.g. `E0505-....tes`, `R001-....tes`; run programs have a `.out` file next to them):

- `tests/stage1_run/`, `tests/stage1_fail/`, `tests/stage1_runtime_fail/`: stage-1-only features.
- `tests/run/`, `tests/compile_fail/`, `tests/runtime_fail/`: shared with stage 0; must behave identically in both compilers.
- `tests/modules/`, `tests/std/`, `tests/stage1_host/`, `tests/web/`.
- `examples/tesseradoom/checks/run_checks.sh`: independent Python checks; run by the suite only when `examples/tesseradoom/WAD/freedoom1.wad` exists.

## Rules for language changes

1. **Spec first.** Describe the change in `language-design.md` (the feature section, a row in section 3 for the new draft, and the draft number at the top) before or together with the code. Anything not in the spec is not part of the language.
2. **Stage 1 only.** Implement in `stage1/` (checker, codegen) and, if needed, `runtime/extra.rs` or `runtime/web.rs`. Do not change stage 0 or the signatures in `runtime/core.rs`.
3. **Stage 1 cannot use a new feature in its own source yet.** The seed does not know it. Implement it without using it, `./build.sh`, then regenerate the seed with `bin/tessera1 emit-rust stage1/main.tes -o bootstrap/tessera1.rs`, run `./build.sh` again (fixpoint), and only then use the feature in `stage1/`.
4. **Tests for every rule.** A passing program in `tests/stage1_run/` with its `.out`, and one file per new diagnostic in `tests/stage1_fail/` (or runtime error in `tests/stage1_runtime_fail/`). Every diagnostic gets a stable code (never reused) and a `help:` line with a concrete fix.
5. **New std module.** Add the file to `std/` (build.sh embeds every `std/*.tes`) and add a branch to `standard_module` in `stage1/main.tes` by hand. Add a test in `tests/std/`. Modules must not reuse built-in function names.
6. **Generated code stays safe.** Generated Rust starts with `#![forbid(unsafe_code)]`; only `runtime/adapter.rs` may use `unsafe`. Tessera semantics (overflow, evaluation order, error format, exit codes) are implemented explicitly, never by relying on Rust behaviour.
7. **Keep the reference in step.** When a user-visible feature changes, update `harness/reference/tessera.md` (and `skills/tessera/SKILL.md` if it changes a workflow or common mistake), then check with `harness/.venv/bin/python harness/harness.py dry-run --variants baseline` (no API cost). A real `harness.py run` costs API money (about $0.02 to $0.04 per task run); ask before starting one.
8. **One way to write it.** Prefer extending an existing construct over adding a second way to say the same thing; record rejected alternatives in section 3 or 19 of the spec.

## Testing graphical programs

`tools/xsend/xsend` sends synthetic clicks and keys (including `keyup`) to a window, on both systems, with the same command line:

    xsend <window> click <x> <y> [button] | key <name> | keyup <name> | close

**X11** (`DISPLAY=:0`): find the window id with `xwininfo -root -tree` (use the line ending in `": ()"`, not the window manager frame) and take screenshots with `import -window <id> shot.png`.

**Windows**: `xsend.exe list` prints every visible window with its handle, and `<window>` may also be a piece of the title (`xsend.exe Tesseradoom key Up`). `xsend.exe <window> size` gives the client size. The events are posted to the window's own queue, so it does not have to be in front. For screenshots:

    powershell -ExecutionPolicy Bypass -File tools/screenshot.ps1 Tesseradoom shot.png

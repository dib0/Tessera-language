# Tessera measurement harness

Measures how changes to Tessera affect two things:

1. **Token cost of code** (`tokens`): real Claude token counts of existing Tessera code, per variant.
2. **How well a model writes Tessera** (`run`): a model solves programming tasks with only a
   language reference; the harness compiles each answer with `bin/tessera1`, runs the tests, and
   feeds compiler errors or the first failing test back, up to 4 attempts per task.

Recorded per task run: passed, passed on the first attempt, compiled on the first attempt,
attempts used, output tokens (including thinking), input tokens, and the token size of the final
program. `summary.md` in each result directory has the table per variant.

## Setup

```sh
./build.sh                                   # builds bin/tessera1
python3 -m venv harness/.venv
harness/.venv/bin/pip install anthropic
```

Credentials: the Anthropic SDK reads `ANTHROPIC_API_KEY`, or a profile created with `ant auth login`.
Nothing is stored by the harness.

## Commands

```sh
# Pipeline check without the API: the reference solutions must pass every task, test set and variant.
harness/.venv/bin/python harness/harness.py dry-run --variants baseline indent-2 indent-4

# Token counts of the examples, tests, compiler source and task solutions per indentation.
harness/.venv/bin/python harness/harness.py tokens

# The model run. Defaults: claude-opus-5-5, effort medium, 4 parallel jobs, 1 repetition.
harness/.venv/bin/python harness/harness.py run --variants baseline indent-2 indent-4 --repeat 2

# Combine result directories into one table.
harness/.venv/bin/python harness/harness.py report harness/results/<dir> ...
```

## Pieces

- `reference/tessera.md`: the language reference the model gets (the complete basis for writing
  programs, modules, web applications and graphical programs). Every complete program in it
  compiles; the other examples are fragments. The Claude Code skill in `skills/tessera/` points to
  this file, so keep it in step with `language-design.md`.
- `reference/features/<name>.md` (none at the moment): extra sections appended for variants that list
  the feature, to try a language feature before it goes into the main reference.
- `variants.json`: variant name -> indentation width, enabled feature sections, and whether the
  model is given the reference at all. The reference and the task's starter code are re-indented to
  the variant's width. `baseline` is the language as specified, without indentation, which is also
  how every file in the harness is stored. Other widths are derived from the nesting of `{ ( [`, so
  code stored at any width renders the same.
- `no-reference` is not a language variant but a measurement of the outside world: `"reference":
  false` gives the model no reference at all, only the rules its answer must follow to be gradeable
  (661 characters against 28,000). It answers one question: does this model already know Tessera?
  Expect 0% until Tessera reaches training data, and run it against each new model release to find
  out when that changes. Two caveats. The `extend-` tasks show Tessera in their starter code, so
  they are the easiest and will move first. And `dry-run` answers with the stored solution without
  reading the prompt, so it passes this variant too and proves nothing about it; only `run` does.
- Web tasks (`kind` `web`, e.g. `web-router`) are programs with `handle` instead of `main`; their tests run
  `app request METHOD PATH` and compare only the status line and the body, so any correct choice of
  headers passes. A test with a `stderr` entry also compares standard error (error messages).
- `tasks/<id>/`: `task.md` (the prompt), `task.json` (kind, suite, allowed effects, tests), `heldout.json`
  (the frozen held-out set), `solution.tes` (reference solution, used by `dry-run`) and `starter.tes`
  (fix and extend tasks). Multi-file tasks have `starter/` and `solution/` directories instead (entry
  `main.tes` plus modules). Generated by `tools/make_tasks_*.py` and `tools/make_heldout.py`.
- Suites: `core` (the 21 original tasks, used while designing the language) and `hard` (four multi-file
  maintenance and policy tasks written after draft 0.21 and not used to change the language). Some
  rules the hard tasks must keep are stated only in `note` declarations in the starter code.
- `results/`: one directory per run, with the full transcript of every task run (git-ignored).

## Test sets

Every task has three test sets, kept apart:

1. **Examples**: the first `examples` tests of `task.json` (default 2), shown in the prompt.
2. **Feedback tests**: all of `task.json`'s `tests` (examples included). The repair loop runs these, and
   on a failure the model sees the arguments, the expected and the actual output. "Passed" in the
   summary means passing this set, so it is partly measured on tests the model has seen.
3. **Held-out tests**: `heldout.json`, never shown and never fed back. They are run once on the
   model's final program (whether or not it passed the feedback tests) and give "Passed held-out".
   A held-out set may also hold `policy` checks on the source (`{"file", "contains"}` or
   `{"file", "absent"}`), for example that an `import ... uses nothing` was not widened.

Expected held-out outputs are written by hand or by small Python oracles from the task text, never by
running the reference solutions; `dry-run` checks that the two agree (this found one wrong reference
solution, `word-count`, which lowercased ASCII only).

The held-out sets are frozen: `harness.py freeze` records their SHA-256 in `heldout.lock`, and `run`
refuses to start when a set differs from the lock. Change a held-out set only before it has been used,
and freeze again deliberately; each result directory's `config.json` records the lock it ran under.

**Test strength** is measured by mutation testing of the reference solutions:

```sh
harness/.venv/bin/python harness/harness.py mutate          # all tasks, about a minute
```

Each mutant changes one operator or integer literal (`<`/`<=`, `==`/`!=`, `+`/`-`, `and`/`or`, ±1, ...);
the report gives per task the share of compiling mutants killed by the feedback tests and by the
held-out tests. Survivors include equivalent mutants that no test can kill.

## Safety

Model-written programs are compiled and executed on this machine. The harness rejects any program
whose `main` declares an effect not allowed by the task (normally only `io` and `env`); Tessera's
effect checking then guarantees the program cannot read or write files or start processes.
Programs run in a temporary directory with a 10 second timeout.

Refusal fallbacks are deliberately not enabled: a fallback would switch to another model in the
middle of a measurement. A refusal is recorded as the outcome `refusal`.

## Cost

The reference is about 7,000 tokens (draft 0.20; it was about 3,000 at draft 0.12) and is cached across requests. With Claude Opus 5.5 at effort
`medium`, a task run averages about 700 to 1,100 output tokens (thinking included) and about 7,000 input tokens,
and almost always passes on the first attempt: roughly $0.02 to $0.04 per task run. 18 tasks x 3
variants x 2 repetitions is 108 task runs, roughly $2 to $4 (measured 2026-11-08). Failing attempts
cost more because the conversation grows. To check the pipeline cheaply first:

```sh
harness/.venv/bin/python harness/harness.py run --tasks fizzbuzz ledger --variants baseline
```
